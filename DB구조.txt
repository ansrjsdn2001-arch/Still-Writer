Still Writer 데이터베이스 구조
==============================

작성 기준
---------
- 기준 DBMS: Supabase가 관리하는 PostgreSQL
- 사용 범위: Supabase는 관리형 PostgreSQL로 사용하고, 인증·인가와 비즈니스 로직은 Spring Boot가 담당합니다.
- 데이터 접근: React는 Supabase에 직접 접근하지 않고 Spring Boot API만 호출합니다.
- 기본 키(PK): 단일 숫자 PK는 BIGINT GENERATED BY DEFAULT AS IDENTITY를 사용합니다.
- 날짜/시간: 절대 시점은 TIMESTAMPTZ(6)로 저장하고 애플리케이션에서는 UTC를 사용합니다.
- 날짜만 의미하는 diary_date와 stat_date는 DATE를 사용합니다.
- JSON 데이터는 JSONB, 긴 본문은 TEXT, 암호화된 바이너리는 BYTEA를 사용합니다.
- PostgreSQL에는 UNSIGNED가 없으므로 음수가 될 수 없는 값은 CHECK (column >= 0)로 제한합니다.
- 상태와 유형 값은 VARCHAR와 CHECK 제약조건을 사용해 Java enum과 명시적으로 매핑합니다.
- 비밀번호와 인증 토큰은 원문이 아닌 해시값만 저장합니다.
- Google Drive OAuth 토큰은 애플리케이션에서 암호화한 뒤 BYTEA로 저장합니다.
- 글, 폴더, 소재는 deleted_at과 purge_after를 이용한 소프트 삭제를 적용합니다.
- 글은 수동 저장 버튼 없이 자동 저장하며, revision으로 오래된 저장 요청을 차단합니다.
- 현재 Supabase DB에는 V001 초기 스키마, V002 문서-외부 파일 연결 테이블, V003 이메일 인증 코드 테이블 마이그레이션을 적용한 구조를 기준으로 합니다.

PostgreSQL 공통 규칙
-------------------
- created_at: TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP
- updated_at: TIMESTAMPTZ(6) NOT NULL DEFAULT CURRENT_TIMESTAMP이며 변경 SQL에서 명시적으로 갱신합니다.
- DB 접속 정보와 암호화 키는 환경 변수로 관리하고 저장소에 원문을 커밋하지 않습니다.
- Supabase의 anon/authenticated 역할에는 애플리케이션 테이블 권한을 부여하지 않습니다.
- 향후 Supabase Data API를 직접 사용할 때만 별도 승인 후 RLS 정책을 설계합니다.

5. 이메일 인증 코드 테이블 (email_verification_codes)
-----------------------------------------------------
목적:
- 회원가입 페이지에서 입력한 이메일로 발송한 인증 코드를 검증하기 위한 테이블입니다.
- 인증 코드 원문은 저장하지 않고 SHA-256 해시만 저장합니다.
- 인증 코드 만료, 검증 완료, 재사용 방지, 시도 횟수 제한을 관리합니다.

| 컬럼명 | 데이터 타입 | 필수 | 제약조건 | 설명 |
|--------|-------------|------|----------|------|
| id | BIGINT | O | PK, IDENTITY | 이메일 인증 코드 고유번호 |
| email | VARCHAR(191) | O | CHECK | 소문자로 정규화한 인증 대상 이메일 |
| purpose | VARCHAR(20) | O | DEFAULT 'SIGNUP', CHECK | SIGNUP |
| code_hash | CHAR(64) | O | | 인증 코드 SHA-256 해시 |
| expires_at | TIMESTAMPTZ(6) | O | CHECK | 인증 코드 만료 시점 |
| verified_at | TIMESTAMPTZ(6) | X | | 인증 성공 시점 |
| consumed_at | TIMESTAMPTZ(6) | X | | 만료·재발송·사용 완료 등으로 더 이상 사용할 수 없게 된 시점 |
| attempt_count | SMALLINT | O | DEFAULT 0, CHECK | 인증 시도 횟수 |
| created_at | TIMESTAMPTZ(6) | O | DEFAULT CURRENT_TIMESTAMP | 인증 코드 생성 시점 |

참고:
- 인증 코드는 알파벳 대문자, 알파벳 소문자, 숫자를 섞어 6자리로 생성합니다.
- 기본 만료 시간은 3분이며 서버 환경 변수로 조정합니다.
- 새 인증 코드를 발송하면 같은 이메일의 기존 미검증 코드는 consumed_at을 기록해 무효화합니다.

------------------------------
| 컬럼명 | 데이터 타입 | 필수 | 제약조건 | 설명 |
|--------|-------------|------|----------|------|

| folder_id | BIGINT | X | FK -> folders.id | 소속 폴더 |
| type | VARCHAR(10) | O | DEFAULT 'GENERAL', CHECK | NOVEL, DIARY, MEMO, GENERAL |
| title | VARCHAR(50) | O | DEFAULT '' | 글 제목 |
| content_json | JSONB | O | | 에디터 본문 데이터 |
| plain_text | TEXT | O | | 검색 및 미리보기용 본문 |
| char_count | INTEGER | O | DEFAULT 0, CHECK >= 0 | 공백 포함 글자 수 |
| char_count_without_spaces | INTEGER | O | DEFAULT 0, CHECK >= 0 | 공백 제외 글자 수 |
| word_count | INTEGER | O | DEFAULT 0, CHECK >= 0 | 단어 수 |
| sentence_count | INTEGER | O | DEFAULT 0, CHECK >= 0 | 문장 수 |
| target_char_count | INTEGER | X | CHECK >= 0 | 글 단위 목표 글자 수 |
| diary_date | DATE | X | | 일기 날짜 |
| status | VARCHAR(20) | O | DEFAULT 'DRAFT', CHECK | DRAFT, IN_PROGRESS, COMPLETED |
| revision | BIGINT | O | DEFAULT 0, CHECK >= 0 | 자동 저장 낙관적 잠금 번호 |
| completed_at | TIMESTAMPTZ(6) | X | | 작성 완료 시점 |
| last_opened_at | TIMESTAMPTZ(6) | X | | 마지막으로 연 시점 |
| created_at | TIMESTAMPTZ(6) | O | DEFAULT CURRENT_TIMESTAMP | 최초 작성 시점 |
| updated_at | TIMESTAMPTZ(6) | O | DEFAULT CURRENT_TIMESTAMP | 마지막 수정 시점 |
| deleted_at | TIMESTAMPTZ(6) | X | | 휴지통 이동 시점 |
| purge_after | TIMESTAMPTZ(6) | X | | 영구 삭제 예정 시점 |

검증 규칙:
- title은 백엔드와 프론트엔드 모두 최대 50자로 제한합니다.
- content_json을 신뢰 가능한 에디터 스키마로 검증한 뒤 plain_text와 통계를 백엔드가 다시 계산합니다.
- target_char_count는 NOVEL에서만, diary_date는 DIARY에서만 허용합니다.
- revision이 요청의 expectedRevision과 일치할 때만 갱신하고 성공 시 1 증가시킵니다.

| 컬럼명 | 데이터 타입 | 필수 | 제약조건 | 설명 |

- 오래된 버전은 보관 개수 또는 기간 정책에 따라 배치로 정리합니다.

17. 글-외부 파일 연결 테이블 (document_external_files)
----------------------------------------------------
목적:
- Still Writer 문서와 Google Drive 같은 외부 저장소 파일의 연결 관계를 저장합니다.
- 문서를 Google Drive로 내보낸 뒤 같은 외부 파일을 다시 갱신할 때 provider_file_id를 기준으로 추적합니다.
- 문서 단위 백업 파일과 단방향/수동 동기화 상태를 관리합니다.
- 외부 파일의 실제 내용은 저장하지 않고, 외부 저장소 계정과 파일 식별자, 동기화 상태만 저장합니다.

| 컬럼명 | 데이터 타입 | 필수 | 제약조건 | 설명 |
|--------|-------------|------|----------|------|
| id | BIGINT | O | PK, IDENTITY | 문서-외부 파일 연결 고유번호 |
| document_id | BIGINT | O | FK -> documents.id | 외부 파일과 연결된 글 |

| mime_type | VARCHAR(191) | X | | 외부 파일 MIME 타입 |
| export_format | VARCHAR(10) | O | CHECK | TXT, DOCX, PDF, MARKDOWN |

| last_synced_at | TIMESTAMPTZ(6) | X | | 마지막 동기화 성공 시점 |

고유 제약조건:
- UNIQUE(external_storage_account_id, provider_file_id)
- UNIQUE(document_id, external_storage_account_id, purpose, export_format)

참고:
- 단순 내보내기는 purpose=EXPORT로 저장합니다.
- 문서 단위 백업 파일은 purpose=BACKUP으로 저장합니다.
- 같은 외부 파일을 계속 갱신하는 단방향/수동 동기화는 purpose=SYNC로 저장합니다.
- Google Drive 파일을 사용자가 직접 수정해 충돌이 발생하면 sync_status=CONFLICT로 표시하고 백엔드가 사용자 선택을 요구합니다.
- 전체 계정 백업처럼 특정 글 하나에 묶이지 않는 백업은 이 테이블이 아니라 별도 backup_jobs/backup_files 테이블을 검토합니다.

소프트 삭제·복구·영구 삭제 정책
-------------------------------
- 글: deleted_at과 purge_after(기본 30일 후)를 함께 기록하고 복원 시 둘 다 NULL로 변경합니다.
- 폴더: 기본 정책은 폴더만 휴지통으로 이동하고 하위 폴더와 글은 유지합니다. 삭제된 폴더 아래 항목은 일반 목록에서 숨기며 복원 시 다시 노출합니다.
- 소재: deleted_at과 purge_after를 기록하고 복원 시 둘 다 NULL로 변경합니다.
- 영구 삭제는 purge_after가 지난 데이터만 백엔드 배치가 처리합니다.
- 글 영구 삭제 시 버전·즐겨찾기·글 태그·글 소재 연결·외부 파일 연결·공유 링크는 CASCADE로 삭제합니다.
- 폴더 영구 삭제 시 documents.folder_id와 하위 folders.parent_id는 SET NULL로 변경합니다.
- 소재 영구 삭제 시 소재 태그와 글 소재 연결을 삭제한 뒤 외부 저장 파일을 정리합니다.
- 외부 파일 삭제와 DB 변경을 하나의 긴 트랜잭션으로 묶지 않고 실패 재시도와 보상 처리를 사용합니다.

검색 정책
---------
- 기본 검색 대상은 documents.title, documents.plain_text, folders.name입니다.
- 초기 구현은 user_id와 deleted_at IS NULL 조건으로 사용자 범위를 먼저 제한한 뒤 ILIKE 검색을 사용합니다.
- 데이터가 증가하면 PostgreSQL pg_trgm 또는 전문 검색 인덱스를 실제 한글 검색 품질 측정 후 도입합니다.
- 정렬 컬럼과 방향은 Java enum 화이트리스트로 변환하며 사용자 입력을 SQL 식별자에 직접 삽입하지 않습니다.

인증·소유권 정책
----------------
- LOCAL 비밀번호는 단방향 해시로 저장하고 GOOGLE·KAKAO 계정은 auth_identities로 연결합니다.
- Refresh Token 원문은 저장하지 않고 해시만 user_sessions에 저장합니다.
- 로그아웃, 비밀번호 변경, 회원 탈퇴 시 관련 세션을 폐기합니다.
- 모든 사용자 데이터 조회·변경 SQL은 인증 user_id와 소프트 삭제 조건을 포함합니다.
- 연결 테이블 등록 전 글·태그·소재가 모두 같은 사용자의 소유인지 Service에서 검증합니다.
- 다른 사용자 리소스는 존재 여부를 노출하지 않도록 일관되게 404로 처리합니다.

자동 저장 정책
-------------
- 클라이언트는 documentId, expectedRevision, saveRequestId, title, contentJson을 전송합니다.
- 백엔드는 contentJson에서 plainText와 글자 수 통계를 다시 계산합니다.
- documents는 최신 상태만 보관하고 document_versions는 복구 가능한 스냅샷만 보관합니다.
- expectedRevision이 현재 revision과 다르면 409 Conflict를 반환하여 오래된 요청의 덮어쓰기를 막습니다.
- 동일 saveRequestId 요청은 멱등하게 처리하여 중복 버전을 만들지 않습니다.
- 자동 저장 간격과 버전 생성 최소 간격은 DB 컬럼이 아닌 서버 설정으로 관리합니다.

아직 적용되지 않은 항목
----------------------
- PostgreSQL JDBC 드라이버, MyBatis, Spring Security, JWT 의존성
- Supabase JDBC 연결 설정과 환경 변수
- 실제 CREATE TABLE 마이그레이션 SQL
- Mapper Interface와 Mapper XML
- Domain, DTO, Controller, Service 및 인증 구현
- 실제 Supabase 프로젝트와 운영 데이터

위 항목은 의존성·설정 변경 승인을 받은 뒤 별도 작업으로 구현하고 검증합니다.
